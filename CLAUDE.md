# Agent Builder - Claude.ai Development Guide

**Purpose**: This guide provides architectural context and development guidelines specifically for Claude.ai when contributing to or modifying the Agent-Builder codebase.

---

## 🎯 Project Purpose

Agent-Builder is a **comprehensive CLI and web application** that generates production-ready AI agents through a sophisticated five-phase pipeline leveraging Claude's extended thinking capabilities.

**Key Outputs:**
- Prompt-based skills for Claude Code (.md files)
- MCP (Model Context Protocol) servers (TypeScript/Python)
- Standalone CLI tools (TypeScript/Python)
- Reusable libraries (TypeScript/Python)

---

## 🏗️ Critical Architecture Decisions

### 1. Five-Phase Pipeline is Sacred

The workflow MUST flow through these phases in order:
```
Research → Clarification → Design → Implementation → Learning
```

**Why**: Each phase builds on the previous one's output. The workflow context (`WorkflowContext`) carries state through all phases.

**Key File**: `/Users/mayankgupta/Github/Work/agent-builder/src/orchestration/workflow-coordinator.ts`

**When modifying workflow**:
- NEVER skip phases (except in specific optimization modes)
- ALWAYS use `context.transitionTo(phase)` when changing phases
- ALWAYS record phase metrics with `recordPhaseMetrics()`
- Maintain backward compatibility with existing context structure

---

### 2. Extended Thinking is Strategic, Not Everywhere

Extended thinking (10K token budget) is used ONLY in these phases:
1. **Research Phase** - Deep domain analysis and capability discovery
2. **Design Phase** - Architectural exploration and trade-off analysis

**Why**: Extended thinking is expensive (tokens + latency). We use it where deep reasoning provides disproportionate value.

**Code Location**:
- Research: `/Users/mayankgupta/Github/Work/agent-builder/src/agents/research-agent.ts` (line 48-56)
- Design: `/Users/mayankgupta/Github/Work/agent-builder/src/agents/design-agent.ts`

**When adding extended thinking**:
- Justify with clear ROI (why does this phase need deep reasoning?)
- Use `claudeClient.completeWithExtendedThinking()` not `complete()`
- Capture thinking traces: `thinkingBlocks` in response
- Budget levels: `low` (2K), `medium` (5K), `high` (10K)

---

### 3. Skill Generation Must Be Ultra-Concise

**CRITICAL CONSTRAINT**: Prompt-based skills MUST be under **200 tokens each** (approximately 50 lines).

**Why**: Skills load into Claude's context window. Context efficiency is paramount.

**Format Requirements**:
```markdown
# Skill Name

## Trigger
- [when condition 1]
- [when condition 2]

## Steps
1. [action 1]
2. [action 2]
3. [action 3]

## Example
User: [brief question]
Agent: [brief response]
```

**What's FORBIDDEN in skills**:
- ❌ Embedded knowledge sections ("Key Knowledge", "Domain Expertise", etc.)
- ❌ Multiple examples (max 1)
- ❌ Verbose explanations or paragraphs
- ❌ Integration point details (belongs in knowledge base)

**What's REQUIRED**:
- ✅ Reference to knowledge base: "Consult knowledge base for [details]"
- ✅ Action verbs: Check, Query, Compare, Alert, Analyze
- ✅ Concrete trigger conditions
- ✅ Brief, numbered steps

**Key Files**:
- Skill generation: `/Users/mayankgupta/Github/Work/agent-builder/src/agents/skill-agent.ts`
- Skill prompt template: `/Users/mayankgupta/Github/Work/agent-builder/src/claude/prompt-templates.ts` (line 306-339)

**When modifying skill generation**:
- ALWAYS validate token count after generation
- NEVER increase the 200-token limit
- Test with: `wc -c file.md` → result / 3.5 should be < 700 bytes

### 4. Knowledge Base Separation

**Domain knowledge lives ONLY in `knowledge-base.md`** (2000-3000 tokens), NOT in individual skills.

**Structure**:
```markdown
# Knowledge Base: [Domain Name]

## Overview
[2-3 sentences on domain]

## Core Concepts
[Key domain concepts and terminology]

## Best Practices
[Industry standards, frameworks, methodologies]

## Common Patterns
[Proven approaches for this domain]

## Anti-Patterns
[What to avoid and why]

## Integration Points
[Systems, APIs, data sources commonly used]

## Contextual Factors
[When to adapt behavior: SLAs, compliance, regions]
```

**Why Separation Matters**:
- Skills remain concise (context efficient)
- Knowledge base is reusable across multiple skills
- Easy to update domain expertise without touching skills
- Claude can load knowledge base once and reference it repeatedly

**Key File**: Generated by research phase, stored alongside skills

### 5. Research Phase Drives Everything

The **Research Agent** performs deep domain analysis that shapes all downstream phases.

**What Research Discovers**:
1. **Domain Classification**: aiops, sales, automation, code, data, support, general
2. **Integration Points**: Tribal knowledge, existing systems, data sources
3. **Advanced Capabilities**: Correlation, learning, context-awareness, prediction
4. **Contextual Factors**: Public vs internal, SLA tiers, compliance requirements
5. **Domain Depth**: Best practices, anti-patterns, industry standards

**Why This Matters**:
- Determines skill sophistication (beyond simple Q&A)
- Identifies what to integrate with (Slack, Jira, Salesforce, etc.)
- Shapes knowledge base content
- Guides design decisions in later phases

**Key File**: `/Users/mayankgupta/Github/Work/agent-builder/src/agents/research-agent.ts`

**When modifying research**:
- Maintain JSON schema structure (required for parsing)
- Add new discovery dimensions to `ResearchFindings` interface
- Update prompt template if adding new research areas
- Research output feeds into ALL downstream agents

### 6. Parallel Execution Pattern

Implementation phase runs THREE agents in parallel:
1. Code generation (implementation-agent)
2. Test generation (testing-agent)
3. Documentation generation (documentation-agent)

**Why**: These are independent tasks - no interdependencies. ~40% speed improvement.

**Critical**: Code MUST be generated first, THEN tests and docs run in parallel (tests/docs need to see the code).

**Implementation**: Uses semaphore-based concurrency control

**Key File**: `/Users/mayankgupta/Github/Work/agent-builder/src/orchestration/workflow-coordinator.ts` (line 234-308)

**When modifying parallelization**:
- Tests and docs CAN fail without failing the build (graceful degradation)
- Use `ParallelBatch` from `/Users/mayankgupta/Github/Work/agent-builder/src/utils/async-utils.ts`
- NEVER parallelize phases with dependencies (e.g., design needs requirements)
- Control concurrency with semaphore limits in config

### 7. Template System: File-Based with Inline Fallbacks

Templates follow a **progressive fallback strategy**:
1. Try loading from `templates/{output-type}/{language}/` directory
2. If files missing, use inline templates from `template-manager.ts`
3. Inline templates guarantee the system never fails due to missing files

**Template Organization**:
```
templates/
├── skill/
│   ├── typescript/
│   └── python/
├── mcp/
│   ├── typescript/
│   └── python/
├── cli/
│   ├── typescript/
│   └── python/
└── library/
    ├── typescript/
    └── python/
```

**Template Engine**: Handlebars with custom helpers

**Key File**: `/Users/mayankgupta/Github/Work/agent-builder/src/templates/template-manager.ts`

**When adding new output formats**:
1. Add new output type to `OutputType` enum in `/Users/mayankgupta/Github/Work/agent-builder/src/types/templates.ts`
2. Create template directory: `templates/{new-type}/{language}/`
3. Add inline fallback in `getInlineTemplates()` method
4. Update PackagingAgent to handle new format

### 8. Memory System for Self-Improvement

Three-tier storage architecture:
1. **Sessions** (`data/memory/sessions/`) - Raw JSONL logs of each build
2. **Patterns** (`data/memory/patterns/`) - Extracted successful patterns
3. **Metrics** (`data/memory/metrics/`) - Aggregated performance data

**Pattern Matching**: Uses cosine similarity on requirement vectors (threshold: 0.7)

**Learning Cycle**:
- Every build → Session captured
- Every 10 sessions → Pattern extraction runs
- Similar patterns → Retrieved during design phase

**Why JSONL**: Append-only, streaming-friendly, time-series optimized

**Key Files**:
- Session storage: `/Users/mayankgupta/Github/Work/agent-builder/src/memory/session-storage.ts`
- Pattern extraction: `/Users/mayankgupta/Github/Work/agent-builder/src/memory/pattern-extractor.ts`
- Pattern matching: `/Users/mayankgupta/Github/Work/agent-builder/src/memory/pattern-matcher.ts`

**When modifying memory**:
- NEVER change JSONL format (breaks existing sessions)
- Pattern similarity threshold (0.7) is tuned - benchmark if changing
- Memory is append-only - no deletions except manual cleanup

## 📋 Development Guidelines

### When Modifying Agent Generation

**DO**:
- ✅ Maintain WorkflowContext structure (backward compatibility)
- ✅ Capture thinking traces when using extended thinking
- ✅ Use Zod schemas for Claude response validation
- ✅ Log progress at key milestones
- ✅ Handle errors gracefully (don't fail entire build if optional step fails)
- ✅ Record metrics for every phase

**DON'T**:
- ❌ Skip phase transitions (use `context.transitionTo()`)
- ❌ Add extended thinking without justification
- ❌ Increase skill token limits (200 tokens is HARD LIMIT)
- ❌ Break JSONL format in memory system
- ❌ Remove inline template fallbacks

### When Adding New Features

**Checklist**:
1. Does this fit into existing five-phase workflow? If not, justify new phase.
2. Should this be a new agent type or enhance existing agent?
3. Does it need extended thinking? (Rare - most don't)
4. Will it work with all output formats (skill/mcp/cli/library)?
5. How will it handle errors? (Graceful degradation preferred)
6. Does it add new config options? Update `config/agent-builder.config.yaml`
7. Does it change WorkflowContext? Update type definitions

### When Fixing Bugs

**Common Issues**:

1. **Extended Thinking Not Working**
   - Check: `(params as any).thinking = { type: 'enabled', budget_tokens: ... }`
   - SDK types may not include thinking - use type assertion

2. **Skills Too Verbose**
   - Validate: Each skill < 200 tokens
   - Check: No embedded knowledge sections
   - Fix: Move knowledge to knowledge-base.md

3. **Template Files Not Found**
   - Check: Inline fallbacks in template-manager.ts
   - Should never fail - fallback is the safety net

4. **Phase Transition Errors**
   - Validate: context.currentPhase matches expected phase
   - Check: Previous phase completed successfully
   - Verify: Required context data exists (design, requirements, etc.)

5. **Parallel Execution Failures**
   - Tests/docs failures should NOT fail build
   - Wrap in try-catch with warning logs
   - Return empty object `{}` on failure

## 🚨 Common Pitfalls

### 1. Embedding Knowledge in Skills
**Problem**: Skills become bloated (>200 tokens)
**Solution**: Move ALL domain knowledge to knowledge-base.md
**Check**: `wc -c skill.md` → divide by 3.5 → must be < 700 bytes

### 2. Skipping Research Phase
**Problem**: Skills lack context and integration points
**Solution**: Research ALWAYS runs first - shapes everything downstream
**Check**: Verify `context.research` exists before design/implementation

### 3. Not Capturing Thinking Traces
**Problem**: Can't learn from extended thinking sessions
**Solution**: Store `thinkingBlocks` in context for learning phase
**Check**: Design/Research results should have `thinkingTrace` field

### 4. Breaking Backward Compatibility
**Problem**: Existing sessions can't be parsed
**Solution**: NEVER change JSONL format or WorkflowContext structure
**Check**: Run build with existing session data after changes

### 5. Over-Using Extended Thinking
**Problem**: Slow builds, high token costs
**Solution**: Reserve for Research & Design only
**Check**: Implementation/Testing/Documentation should use standard completion

## 📊 Performance Characteristics

**Typical Build Times**:
- Research: 3-5 minutes (extended thinking)
- Clarification: 2-3 minutes (2-3 rounds)
- Design: 5-10 minutes (extended thinking)
- Implementation: 5-8 minutes (parallel)
- Learning: < 1 minute
- **Total**: 15-25 minutes

**Token Usage**:
- Research: ~8-12K tokens (including thinking)
- Design: ~10-15K tokens (including thinking)
- Implementation: ~15-20K tokens (code + tests + docs)
- **Total**: ~35-50K tokens per agent

**Optimization Targets**:
- Clarification rounds: Reduce from 3 to 2 (save 2-3 min)
- Parallel agents: Ensure all 3 run concurrently (not sequentially)
- Extended thinking: Only where justified (don't add more)
